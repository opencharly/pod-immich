# 2026.324.0914 — fix(immich)!: rename the pnpm pin var to stop shadowing layer-nodejs's

## Summary

Renames the pnpm pin this candy installs for the Immich v3.4.1 from-source build from the un-namespaced `PNPM_VERSION` to `IMMICH_PNPM_VERSION`, so it stops shadowing `layer-nodejs`'s identically named pin inside any image that composes both. Closes opencharly/pod-immich#15.

**Round 3 (this head) reconciles the DECLARED `layer-nodejs` pin with the tag the image actually RESOLVES** — round 2 named one tag in the Summary and composed another in the probe without reconciling them, and that is now stated as the two artefacts they are (see below). Round 2 itself fixed the two A3 findings of round 1: the tier is the one the pasted evidence earns, and the harness/model pair is evidenced rather than asserted. The TREE has been identical since round 1 (`740b7ec^{tree}` == `5406a29^{tree}`), so every tree measurement below is still a measurement of this head.

**The defect (measured).** A candy's `var:` values are exported as image ENV, so this candy's `PNPM_VERSION` was never a private knob — it was GLOBAL. Inside the image that reds, `pod-immich` exports `PNPM_VERSION=12.15.0` into the image env, and `layer-nodejs`'s measurement check reads that same ENV name — so it sees pod-immich's value instead of its own `10.33.4`.

**Declared pin vs resolved tag — two different artefacts, and this is where round 2 was incoherent.** The candy DECLARES one tag; the CachyOS image COMPOSES another:

| artefact | value |
|---|---|
| declared here, in `require:` (`charly.yml`) | `@github.com/opencharly/layer-nodejs:v2026.272.0322` |
| RESOLVED into the image that reds | `layer-nodejs v2026.314.0707` — measured in the failing bed's build tree as `.build/_candy/nodejs.v2026.314.0707` |

The resolver unifies the two declarations: one candy in the CachyOS chain requires the newer `layer-nodejs`, and two differing tags of one candy in one scope would otherwise be a load error. That resolution is also readable on this host, independent of the bed: `distro-cachyos`'s immich worktree carries `.build/_candy/nodejs.v2026.314.0707` while every manifest in that tree — `box/immich-cdi/charly.yml` among them — declares `v2026.272.0322`, and the candy that requires the newer tag there is `ai-toolkit.v2026.321.1053`. So the failing check is the RESOLVED tag's `plan:candy:…layer-nodejs:9` — and the measurement check **does not exist at `v2026.272.0322` at all** (it was added at `v2026.280.2136`; measured with `git -C layer-nodejs grep -c "allowBuilds git-key form matches the recorded measurement" <tag> -- charly.yml`, which is `0` at the declared tag and non-zero from `v2026.280.2136` on). The declared tag therefore never could run it; the resolved one does.

In `opencharly/distro-cachyos` `check-cachyos-immich-pod` (run `2026.324.0820`) the image built, and then exactly **one** check of 123 failed:

```console
FAIL check the pinned pnpm version's allowBuilds git-key form matches the recorded measurement [plan:candy:github.com/opencharly/layer-nodejs:9] exit=1
stderr: pnpm 12.15.0 is UNMEASURED for the allowBuilds git-key form. Bump only with a measurement ...
```

The previous pod-immich tag (`v2026.274.0650`) exported no pnpm var at all, so the collision arrived with the v3 cutover (`v2026.320.0058`).

**The fix is a rename, not a behaviour change.** The pin's value, the download URL shape, the tarball, the destination and the `--version` probe are untouched:

| site | before | after |
|---|---|---|
| `charly.yml` `var:` | `PNPM_VERSION: "12.15.0"` | `IMMICH_PNPM_VERSION: "12.15.0"` |
| `charly.yml` plan step | `…/download/v${PNPM_VERSION}/pnpm-linux-${PNPM_ARCH}.tar.gz` | `…/download/v${IMMICH_PNPM_VERSION}/pnpm-linux-${PNPM_ARCH}.tar.gz` |
| `.agents/skills/immich-layer/SKILL.md` | — | records WHY the var is namespaced, and the one check the collision reded |

The old name is deleted outright — no alias, no dual path, no compatibility shim — and the claim-keyed sweep below is pasted with its positive control. The only in-org reader of that name is `layer-nodejs`'s own pin and its measurement check, which is precisely why this candy moves off it.

## Change classification

**Breaking change + rollback:** the image built from this candy no longer exports `PNPM_VERSION`; the pin is exported as `IMMICH_PNPM_VERSION`. That breaks exactly one thing — a consumer reading this candy's pnpm pin out of the image environment — and the value was never safe for a consumer to read (it was shadowing, and shadowed by, `layer-nodejs`'s pin). The install itself is unchanged: the same release tarball from the same URL template, into the same directory, with the same `--version` probe — proven above by the second probe image, which installs 12.15.0 through the namespaced interpolation. So there is **no migration, no state to move and no data to convert**. Rollback is a plain `git revert` of the code commit (`5406a29`), which restores the old env name — and with it the collision.
