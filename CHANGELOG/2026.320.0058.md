# 2026.320.0058 — feat(immich)!: build Immich v3.4.1 and carry the ML backend in the image

## Summary

Takes the `immich` candy from **v2.7.5** to upstream **v3.4.1** and folds the machine-learning backend into it, so one candy carries the whole Immich stack. The separate `immich-ml` candy/image is retired (`opencharly/pod-immich#12`).

Round 2 (this head) fixes the two claim defects the validator found in round 1: the skill documented `--extra cuda --extra cuda-libs` (a command the build fails on — `cuda-libs` is a **dependency group**, so `--group cuda-libs`), and it cited a bed that ships with the follow-on `distro-cachyos` PR rather than one that exists here. Both are corrected in `.agents/skills/`.

**Why v3.4.1 is not a version bump.** The from-source recipe moved in almost every step — each item below is read off the v3.4.1 release tree (`server/Dockerfile`, `package.json`, `mise.toml`, `machine-learning/pyproject.toml`, `server/src/**`):

| before | v3.4.1 |
|---|---|
| one `pnpm install` + `--filter immich deploy --prod` | `@immich/sdk` → `@immich/plugin-sdk` → server, then a **mandatory sharp rebuild** against the system libvips |
| `plugins/` → `/build/corePlugin` | `packages/plugin-core` → `/build/plugins/immich-plugin-core/{dist,manifest.json}`, extism-js 1.7.0 |
| geodata without `countryInfo.txt` | `countryInfo.txt` is required (read unguarded at boot); geoJSON pinned to natural-earth `v5.1.2` |
| `node …/dist/main` | ESM entry — `node …/dist/main.js` |
| pnpm 10.x single-file binary | pnpm **12.15.0** (the repo's own `packageManager` pin; 12.x ships a tarball) |
| ML in a sibling candy/image | ML in this candy: uv venv on Python 3.13, `--extra cuda --group cuda-libs` |

**The ML backend here.** `uv sync --frozen --no-dev --no-editable --active --link-mode copy --extra cuda --group cuda-libs` builds `/opt/immich/machine-learning/.venv` with ONNX Runtime's `CUDAExecutionProvider` and its own CUDA-12 wheels (an Arch/CachyOS base ships CUDA 13, which `onnxruntime-gpu` 1.27 cannot load). A charly-owned wrapper `/opt/immich/ml-run.sh` puts those wheel `lib` dirs on `LD_LIBRARY_PATH`, activates the venv, and execs `python -m immich_ml`; the supervised `immich-ml` service (priority 40) and the CUDA-provider probe both go through it, so the loader path is computed once. The server is pointed at it with `IMMICH_MACHINE_LEARNING_URL=http://127.0.0.1:3003`, because upstream's default names the docker-compose service `immich-machine-learning`.

**Three runtime facts the build alone does not reveal** — each found by the gate, root-fixed, re-proved:

1. uv's managed CPython defaulted to `~/.local/share/uv/python` — mode 0700 under `/root`, so the venv's `bin/python` symlink was unreadable to the image's uid-1000 user and every probe died with `exit=126 Permission denied` while the build succeeded. Fixed with `UV_PYTHON_INSTALL_DIR=/opt/immich/python` (+ `chmod -R a+rX`).
2. `immich_ml/__main__.py` starts its worker by exec'ing the bare `gunicorn` from PATH, so the venv must be active — without it the exec resolved the base image's system python and died with `/usr/sbin/python: No module named gunicorn`.
3. `immich_ml`'s `NonPrefixedSettings` reads **`IMMICH_HOST` / `IMMICH_PORT`** (not the `MACHINE_LEARNING_*` prefix), and this image sets `IMMICH_PORT=2283` for the server — so the service overrides them to `0.0.0.0:3003`, or the ML backend binds the server's port and crash-loops.

**Skills/docs in the same commits:** `immich-layer` and `immich` rewritten for v3.4.1 + the merged ML backend (present tense, no `/charly-immich:immich-ml*` addresses), `README.md` and `AGENTS.md` updated, and `AGENTS.md`'s stale "the `skill:` entity is the source, never edit `SKILL.md`" claim corrected to the current contract.

Run history, with the one unresolved event named rather than explained away: four build attempts settled the four defects above. A fifth attempt was terminated by `SIGKILL` at `buildctl` before any step ran (`#1 [internal] load build definition`), producing no artifact. **What is known:** a second `buildctl` from another session on this host was holding buildkit's `sharing=locked` cache mounts (which serialize builds), and the killed process had been waiting at `#1` for over 30 minutes on a host with 84 GB free. **What is not known:** what sent the signal — neither `dmesg` nor the user journal carries an OOM record for that window. That gap IS the finding, and it is filed as **opencharly/charly#1161** with the evidence, the diagnosis that is missing and a repro sketch. It is not claimed here to be load-related, benign, or resolved, and the green builds that followed are not offered as evidence about it. A prototype variant that pointed the box at the OCI base image directly (instead of the box ref) was reverted because it changes how the bootstrap resolves the image's user — it exists only in a scratch project, never in this diff.

**Filed, not swallowed:** the ML service logs an upstream warning that it cannot fix `libtensorrt_rtx.so` symlinks inside `onnxruntime_ep_nv_tensorrt_rtx` — an EP package that Immich's own `cuda` extra pulls in. The provider it warns about is not the one this image selects (the build-scope probe asserts `CUDAExecutionProvider`, present and working) and the service does not fail, so the package is left exactly as upstream pins it instead of being patched around in site-packages. Whether that EP is supported on a venv layout is filed as **opencharly/pod-immich#14** with both options an owner can choose.

## Change classification

- **Kind:** candy (behavioral) + its skills/docs. No schema, no pin, no Go change.
- **Blast radius:** every consumer of `immich` gets a v3.4.1 server, a new `immich-ml` service on 3003, a `models` volume, and a much larger image (CUDA wheels in the venv). The candy's name, route, port 2283, library/cache/import/external volumes, `env_provide`/`env_accept` and `secret_accept` are unchanged.
- **Rollback:** revert these two commits; the previous tree pins v2.7.5 and carries no ML backend. A deployment rolled back to it ignores the `models` volume.
- **Breaking change + rollback:** the `!` marks a hard cutover for the **`immich-ml` role**, not for this candy's address: any box or deploy composing `@github.com/opencharly/pod-immich-ml` loses that candy, its `models` volume and its port 3003, and `/charly-immich:immich-ml` + `/charly-immich:immich-ml-layer` stop resolving in the marketplace corpus — that content is now here, in `immich`. Consumers move by composing `pod-immich` alone. Roll back by reverting these commits and pinning `pod-immich-ml` back to `v2026.274.0811`, which restores the candy and both skill files unchanged.

## Filed issues

Two findings are separable from this change and are filed rather than fixed here:

- **opencharly/charly#1161** — `buildctl` died with `SIGKILL` while waiting on buildkit's locked cache mounts; the diagnosis (what sent the signal) does not exist and the build driver should provide it. Non-blocking for this diff: no artifact was produced and nothing in it is implicated.
- **opencharly/pod-immich#14** — the `libtensorrt_rtx` symlink warning from the `cuda` extra's TensorRT-RTX EP; the EP is unused here and the service is healthy, so the choice between "pin the package set" and "carry upstream's extra whole" belongs to an owner, not to a silent suppression.

Everything else this change surfaced was blocking for it and is fixed in it (see R1). The retirement of the sibling repo is tracked by `opencharly/pod-immich#12`, which this PR closes.
