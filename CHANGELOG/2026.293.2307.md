# 2026.293.2307 — docs(immich): name the real consumer of the immich provide

## Summary

Two comments in this candy's manifest claimed `openwebui` consumes the immich provide:

```
Consumers like openwebui and hermes already declare this env var in their env_accept.
openwebui and hermes declare the same secret_accept entry with the same key path …
```

The declarations existed; the consumption never did. Open Web UI has no immich integration, so
`openwebui` accepted `IMMICH_API_URL` and the shared `charly/api-key/immich` secret without any
code path reading either. That is dead weight in the consumer, not a contract.

`opencharly/pod-openwebui#15` removes both declarations there. This change makes **this**
candy's comments true, so the next reader is not sent looking for a consumer that does not
exist and cannot "fix" it by re-adding the accepts.

`hermes` remains the real consumer: same `env_accept`, same `charly/api-key/immich` secret
path, so one `charly secrets set charly/api-key/immich <key>` still populates it.

## How tested

Prose-only change in a candy manifest; no packages, services, plans, or provide/accept
semantics altered.

```
$ charly -C <worktree> box validate
charly box validate: OK — checked 11 candies, 7 distros, 7 builders; 0 warnings, 0 errors
```

The behavioural side of this pair is proved on the other side of the change: in
pod-openwebui#15, a compose of `pod-immich` + `pod-openwebui` generates and runs with the
accepts removed, which is what makes them removable at all.
